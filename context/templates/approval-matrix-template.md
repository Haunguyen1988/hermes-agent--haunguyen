# Approval Matrix Template

Use this template when Hau needs to define, clarify, or document approval authority for requests, access, process changes, project decisions, documents, or operational governance activities.

The purpose of this template is to make approval flow clear, traceable, and practical for execution.
It should reduce ambiguity between requester, reviewer, approver, executor, and informed parties.

---

# [Approval Matrix Title]

## 1. Purpose
State why the approval matrix is needed.
Examples:
- define approval authority for user access and role changes
- clarify approval flow for SOP issuance
- support project governance and decision control
- standardize approval responsibility across departments

## 2. Scope
Define what the matrix covers.
Examples:
- system access requests
- SOP / document approval
- project change requests
- vendor-related decisions
- reporting / dashboard release
- operational exception approval

## 3. Approval Matrix

Use this baseline structure:
- ID
- Request / Decision Type
- Description
- Requester
- Reviewer
- Approver
- Executor
- Informed Parties
- SLA / Timeline
- Evidence / Record
- Note / Exception

### Guidance For Each Column

**Request / Decision Type**
State the type of item requiring approval.
Examples:
- new user creation
- role change
- SOP issuance
- production change
- access revocation
- project scope adjustment

**Description**
Briefly explain what is being approved.

**Requester**
State who initiates the item.

**Reviewer**
State who performs preliminary review if applicable.
This may include business owner, PIC, key user, or ICT check.

**Approver**
State the decision authority.
Do not leave this ambiguous.

**Executor**
State who carries out the approved action.
This should be distinct from approver unless explicitly intended.

**Informed Parties**
State who should be notified after approval or execution.

**SLA / Timeline**
State expected timing where relevant.

**Evidence / Record**
State what proof or record should exist.
Examples:
- approval email
- signed form
- system ticket
- tracker entry
- version control record

**Note / Exception**
Capture exception logic such as urgent approval, temporary access, or delegated authority.

## 4. Approval Rules
State any general rules that govern the matrix.
Examples:
- approver must be department manager
- executor cannot self-approve
- urgent cases require post-facto documentation
- access requests require business justification

## 5. Escalation / Exception Handling
Describe what happens when:
- approver is unavailable
- urgent approval is needed
- approval is rejected
- conflicting approval views exist
- the request falls outside standard scope

## 6. Record Retention / Governance Note
Describe how approval evidence should be stored or tracked.

## Short Matrix Mode

When the user needs a compact version, reduce the table to:
- Request Type
- Requester
- Approver
- Executor
- Record
- Note

## Writing Rules For This Template

When using this approval matrix template:
- separate requester, approver, and executor clearly
- support traceability and auditability
- avoid unclear approval ownership
- include exception logic when practical
- keep the matrix usable for operations, ICT, and management

## Quality Standard

A good approval matrix should help Hau:
- clarify governance quickly
- reduce approval confusion
- standardize responsibility
- support SOP, access, project, and change control processes
