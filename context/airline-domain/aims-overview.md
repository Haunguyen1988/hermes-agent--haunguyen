# AIMS Overview

## Purpose Of This Context File

This file provides a practical working overview of AIMS as used in Hau's context.
It is not intended to be a vendor manual or a highly technical system specification.
It should help the agent understand how to frame AIMS-related work in operational, documentation, implementation, and management terms.

## AIMS In Hau's Working Context

AIMS should be treated as an operational system platform that supports airline business and operational processes across multiple departments.

In Hau's context, AIMS-related tasks often involve:
- operational process support
- cross-department workflow alignment
- user access and role management
- implementation planning
- system issue handling and escalation
- fit-gap clarification with vendor
- document and SOP development
- translation of system capability into business/operational use

## Typical Business Perspective

When discussing AIMS, the assistant should not describe it only as software.
It should be treated as a control and workflow enabler that can affect:
- operational continuity
- data ownership and visibility
- departmental responsibility
- process standardization
- implementation complexity
- vendor dependency
- management decision-making

## Common Working Themes

Typical AIMS-related themes in Hau's work include:
- user creation and access approval flow
- access segregation and department scope
- issue escalation and service recovery
- process mapping between departments and system steps
- implementation planning by function or department
- clarification of vendor capability versus business expectation
- preparation of management-facing summaries
- translation of raw system topics into SOP-ready content

## Departments Commonly Connected To AIMS Topics

The agent should commonly assume involvement from one or more of these parties:
- OCC
- Crew
- Maintenance
- Ground Ops
- ICT
- Vendor / support team
- management / business owners

The exact group depends on the process being discussed.

## AIMS Analysis Lens

When analyzing an AIMS-related topic, prefer this thought sequence:
1. What business or operational process is involved?
2. Which departments own or touch the process?
3. What part of the process is supported or constrained by AIMS?
4. What user role, access right, or data scope is affected?
5. What risk exists if the process is unclear, delayed, or unsupported?
6. What output is needed: SOP, memo, summary, checklist, fit-gap, action log, or workshop question?

## User And Access Perspective

When the topic involves user management or access rights, the agent should distinguish between:
- requester
- department manager or approver
- AIMS PIC / coordinator
- ICT / system administrator
- key user
- vendor / support team

The assistant should emphasize:
- ownership of request
- approval authority
- execution responsibility
- access scope and data segregation
- review / modification / revocation when relevant

## Issue And Service Perspective

When the topic involves incident, malfunction, or service interruption, the agent should think in operational sequence:
- detection
- initial confirmation
- user impact assessment
- escalation to PIC / ICT / vendor
- temporary workaround if needed
- service recovery validation
- closure and RCA if required

The assistant should frame AIMS issues as operational risks, not only technical faults.

## Implementation Perspective

When the topic involves rollout or system change, the assistant should view AIMS through an implementation lens:
- current state versus target state
- department readiness
- process dependency
- required clarification from vendor
- configuration or access implications
- operational impact during transition
- risk and decision points

## Communication Perspective

When converting AIMS content for different audiences:

### For working teams
- explain workflow clearly
- define ownership
- identify practical next steps

### For vendors
- separate confirmed function from open question
- use precise wording
- avoid overstating internal assumptions

### For management
- reduce technical detail
- highlight implication, risk, and recommendation
- focus on why the topic matters to operations or governance

## Output Expectation

Good outputs created using this context should help Hau:
- prepare or optimize SOPs
- clarify workflows and responsibilities
- build implementation or fit-gap materials
- prepare vendor discussions
- summarize system topics for leadership
- turn scattered information into operationally usable artifacts
