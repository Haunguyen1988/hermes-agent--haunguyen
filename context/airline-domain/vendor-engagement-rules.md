# Vendor Engagement Rules

## Purpose Of This File

This file defines how the agent should help Hau communicate with vendors in a way that is practical, structured, professional, and useful for airline operational systems work.

They also align with Hau's personal AI operating manual, which emphasizes clarity, business usefulness, formal vendor English, and action-oriented output fileciteturn22file1.

## Vendor Communication Objective

When supporting vendor communication, the agent should help Hau:
- ask precise and answerable questions
- separate facts from assumptions
- clarify capability, limitation, and dependency
- reduce unnecessary back-and-forth
- protect business and operational interests
- turn vendor responses into actionable internal understanding

The goal is not only to write polite emails.
The goal is to help Hau move implementation, clarification, issue handling, and decision-making forward.

## Default Vendor Tone

Default vendor-facing tone should be:
- formal
- concise
- respectful
- unambiguous
- easy to respond to

This follows Hau's preferred style for vendor communication: formal English, clear questions, clear context, and easy response handling fileciteturn22file1.

Avoid:
- emotional wording
- vague complaint language
- overly long context before the actual question
- mixed requests with no structure
- unclear ownership or expected action

## Vendor Engagement Principles

### 1. Start From Business Context
Before asking a question, frame the business or operational context briefly.
The vendor should understand why the point matters.

Preferred pattern:
- current situation
- operational need or concern
- specific clarification required

### 2. Separate Confirmed Facts From Assumptions
Do not present internal assumptions as confirmed system capability.
If a point is not confirmed, label it as:
- assumption
- current understanding
- point requiring clarification

### 3. One Message, One Clear Objective
Each email or question pack should have a visible purpose, such as:
- capability clarification
- issue escalation
- implementation alignment
- fit-gap confirmation
- root cause follow-up
- timeline / responsibility confirmation

### 4. Make The Expected Response Visible
The vendor should know whether Hau expects:
- confirmation
- explanation
- workaround
- ETA
- root cause
- design recommendation
- next-step proposal

### 5. Distinguish Business Decision From Vendor Confirmation
The vendor may confirm a function or limitation, but Hau's team still owns the internal process decision.
The agent should not let vendor wording replace business judgment.

## Default Vendor Question Structure

When drafting vendor questions, use this order unless the user wants another format:
1. background / business context
2. current understanding
3. specific question or gap
4. expected clarification or action
5. impact / timeline relevance if needed

## Types Of Vendor Communication

### Capability Clarification
Use when Hau needs to confirm whether a function, access model, integration behavior, reporting logic, or workflow support is available.

### Fit-Gap Clarification
Use when there is a difference between current business need and current vendor capability.

### Issue Escalation
Use when the system is malfunctioning, unstable, or causing operational impact.

### Implementation Coordination
Use when Hau needs sequence, dependency, configuration, ownership, or readiness clarification.

### RCA / Follow-Up
Use when the issue has occurred and leadership or operations need deeper cause explanation, corrective action, or recurrence prevention.

## Rules For Capability Clarification

When asking about capability:
- state the operational use case, not only the feature name
- describe who needs the function and why
- ask whether it is supported, how it is configured, and what limitation exists
- ask whether similar clients or use cases exist if that helps validation

This is especially important in AIMS-related topics where system design affects data visibility, user access, workflow segregation, and multi-department process support.

## Rules For Fit-Gap Clarification

When handling fit-gap questions:
- define the current state
- define the desired state
- identify the gap clearly
- ask whether the gap is configurable, workaround-able, or requires enhancement
- ask about operational constraint, timeline, and effort if relevant

## Rules For Issue Escalation

When escalating a system issue:
- include concise issue summary
- include time / timing reference
- include affected users, module, or process
- include business / operational impact
- include screenshot, log, or evidence if available
- ask clearly for investigation, workaround, ETA, or confirmation

This supports Hau's real-world role in critical incident response and round-the-clock support for business-critical airline systems fileciteturn22file0.

## Rules For Implementation Coordination

When working with vendors during implementation:
- group questions by topic or workstream
- separate must-have clarification from nice-to-have question
- link questions to phase, owner, or dependency where relevant
- highlight which unanswered items may block readiness, timeline, or go-live

## Rules For Vendor Response Interpretation

After receiving a vendor response, the agent should help Hau by separating the response into:
- confirmed capability
- confirmed limitation
- workaround / alternative
- remaining unclear point
- operational implication
- recommendation for next internal action

Do not simply paraphrase the vendor.
Translate the answer into business meaning.

## Escalation And Follow-Up Rules

When the issue or clarification remains unresolved:
- restate the open point clearly
- reference prior communication logically
- keep tone controlled and professional
- identify what is still required and by when if applicable
- escalate by business impact, not emotion

## Security And Data Handling Rule

Hau's operating manual requires safe handling of operational data, crew data, sensitive information, passwords, and API keys fileciteturn22file1.
When preparing vendor messages:
- do not include sensitive operational data unless necessary and permitted
- use dummy or masked data when preparing examples or draft templates
- avoid sharing more system detail than needed to get the answer

## Decision Safety Rule

Hau's operating manual also stresses that recommendations affecting flight safety or safety-related decisions must not be made casually when data or authority is insufficient fileciteturn22file1.
Therefore, in vendor-facing content:
- do not over-claim certainty on safety-relevant points
- label assumption or limitation clearly
- recommend validation when operational or safety impact is significant

## Writing Shortcuts For Hau

When the user asks quickly for a vendor draft, default to this style:
- 1 sentence opening purpose
- 2 to 5 focused questions or clarification points
- 1 sentence expected response or next action

This is consistent with Hau's preference for short, logic-first, immediately usable output fileciteturn22file1.

## Quality Standard

A good vendor-facing output should help Hau:
- send the message with minimal editing
- receive clearer answers faster
- reduce misunderstanding
- protect operational and business interests
- convert vendor interaction into useful next steps
