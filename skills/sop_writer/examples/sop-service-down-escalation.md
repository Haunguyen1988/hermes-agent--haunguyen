# Example — SOP Service Down Escalation

## Use Case
Draft a service disruption SOP for AIMS when users cannot access the system or a critical function is unavailable.

## Example Prompt
Write a concise internal SOP for AIMS service down handling, including detection, escalation, vendor contact, workaround, recovery validation, and closure.
Audience: AIMS PIC, ICT, affected departments.

## Example Output

# SOP — AIMS Service Down Handling

## 1. Purpose
This procedure defines the actions required when AIMS or a critical AIMS function is unavailable or unstable, in order to minimize operational disruption and ensure timely escalation and recovery.

## 2. Scope
This procedure applies to all major AIMS service interruptions affecting access, core workflow, or data availability.

## 3. Responsibilities
### 3.1 Users / Affected Departments
- Report the issue immediately to the AIMS PIC or ICT.
- Provide screenshot, time, and affected function if available.

### 3.2 AIMS PIC
- Confirm the issue scope and business impact.
- Coordinate internal escalation and vendor contact.
- Provide progress updates to concerned stakeholders.

### 3.3 ICT
- Support technical verification and local troubleshooting.
- Coordinate with vendor on system-side investigation.

### 3.4 Vendor
- Investigate the issue.
- Provide workaround, correction status, or ETA.

## 4. Procedure
### 4.1 Detection
Any user identifying an AIMS failure shall report it immediately.

### 4.2 Initial Verification
The AIMS PIC and/or ICT shall verify:
- affected module or function
- number of impacted users or departments
- operational criticality

### 4.3 Escalation
If the issue cannot be resolved immediately internally, the AIMS PIC shall escalate to vendor support with:
- issue summary
- occurrence time
- affected area
- business impact
- supporting evidence

### 4.4 Workaround
Where available, a temporary workaround shall be communicated to affected users.

### 4.5 Recovery Validation
After vendor or ICT confirms restoration, the AIMS PIC and selected users shall validate system availability and function.

### 4.6 Closure
The case shall be closed only after:
- service is confirmed restored
- key users can perform required actions
- follow-up record is updated

## 5. Records
- incident log
- vendor ticket
- communication record
- recovery confirmation
